# 04 東京23区の OSM ノード密度

## 依頼

> 東京23区の OSM の全ノード（約 966 万点）の密度をヒートマップで見たい。拡大・移動したら、タイルの粗い集計ではなく、その画面の解像度で数え直してほしい。PC のブラウザで。

## 読み取った要件

| 要件 | 数値にしたもの |
| --- | --- |
| 画面の解像度で数え直す | 毎フレーム、全点を数え直す。全体が見えているとき、ピクセルごとの数の合計が点数 (9,658,062) と一致することを毎回確かめる |
| 拡大・移動が滑らか | 23 区全体から渋谷駅周辺まで 256 倍ズームして戻る 300 フレームで frame_ms p95 8.3 ms 以下。最悪の全体表示も別に p95 8.3 ms 以下 |
| 画面に出ている | 渋谷駅の画面中央が空の色でないこと、色の段階のいちばん明るい色まで出ていることを、読み戻して確かめる |
| 開ける | データ gzip 20 MB 以下、初回描画 p50 2 s 以下 (ローカル配信) |

## やらないこと

タイル、事前集計、タグや種類での絞り込み、地名や背景地図、点のクリック。ノードの属性は使わず、位置だけを持つ。

## 設計

- 点は位置だけを持つ。23 区の枠 (139.55–139.93°E、35.50–35.83°N) の中を経度に cos(緯度) を掛けた正方グリッドで 16 ビットに量子化 (約 0.5 m)。抽出には枠の外のノードが 1,872 個 (海や島へ延びるリレーションの構成ノード) 含まれていて、これを入れると外接矩形が 1,500 km になり、量子化の 1 刻みが約 13 m に粗くなる。だから枠で切る。
- ベイク時に Morton 順に並べ、差分 (2^16 で折り返す) で保存する。Morton 符号は座標を両方含むので、符号を数値として並べ替えるだけで済む。gzip 後は 17.5 MB。
- 毎フレーム 3 段:
  1. 全点を 1 px の点として R32F に加算ブレンド (= ピクセルごとの数)。
  2. 4×4 ごとの max を 1×1 まで縮約する。
  3. log(1 + 数) / log(1 + 最大) で色付け。
  最大値を CPU に読み戻さないので、色の尺度は GPU の中だけで画面に合わせて変わる。
- 読み込み時に、Morton 順の点を 128 本のストライドに分けて並べ直す。地上で隣り合う点が描画順で離れ、同じピクセルへのブレンドの競合が減る。全体表示の GPU 時間は 11.7 ms から 2.6 ms になった (RTX 3060。ストライド 16: 5.4、64: 2.7、256: 3.3、4096: 7.6 ms。離しすぎるとキャッシュが効かなくなる)。

## 計測で分かったこと

- 全体表示と街区表示で、コストの性質がまったく違う。全体表示では全点がどれかのピクセルに描かれ、ブレンドが競合する (1 ピクセル最大 803 点)。街区表示ではほぼ全点がクリップされ、頂点処理だけになる (0.75 ms)。カメラ経路の p95 だけでは全体表示の最悪値が隠れるので、別の予算にした。
- R32F テクスチャのフィルタを NEAREST にし忘れると、テクスチャが不完全になり、texelFetch がすべて 0 を返す。数の合計の検査はカウント用のフレームバッファを直接読んでいたので通ってしまい、画面は真っ黒だった。画面に出た色を読む検査を加えた。
- 読み込み時の並べ替えの式に不具合があった (2026-10-30 に修正)。ストライドの間隔を一律に ceil(n / S) にしていたので、最後のストライドが配列の外に 49 点はみ出し、南東の 49 点が消えて北西の角 (0, 0) に存在しない点が 49 個できていた。合計は変わらないので数の合計の検査は通っていた。全体表示の画素ごとの数を CPU の数え直しと比べる検査を足した。

## WebGPU との比較

同じ依頼を WebGPU の compute で数える [webgpu-004-osm-node-density](../webgpu/004-osm-node-density/REQUEST.md) を作り、同じブラウザ、同じデータ、同じ経路で比べた (RTX 3060、2026-10-30)。GPU 時間は WebGPU のほうが 4〜5 倍短い (全体表示 2.64 ms に対して 0.51 ms)。完了を待つフレーム時間は、ズーム経路の p50 でこちら (1.06 ms) のほうが短い。WebGPU は完了の通知に約 2.3 ms かかるため。
