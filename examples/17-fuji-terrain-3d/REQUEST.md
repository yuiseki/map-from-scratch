# 17 富士山の地形を 3D で回す

## 依頼

> 富士山のまわりの地形を、3D で斜めから眺めたい。PC のブラウザで、なめらかに回したい。

## 読み取った要件

| 要件 | 数値にしたもの (spec.yaml の evaluation.budgets) |
| --- | --- |
| 3D で斜めから眺めたい | close 視点 (距離 12 km、pitch 25°) で最も細かい段 L0 (15.6 m) が 50 チャンク以上、すべて代替なしで描けている |
| なめらかに回したい | 回転 120 フレームで GPU 完了までの frame_ms p95 8.3 ms (120 Hz)、gpu_ms p95 4 ms、cpu_ms p95 2 ms。最も重い low 視点と close 視点も 8.3 ms。先読みなしの回転とズームでは、読み込みと復号を挟んだ 1 フレームの全費用が p95 8.3 ms、最大 33.3 ms (60 Hz で落とすのは 1 フレームまで)。入力から描画命令まで 4 ms。先読みのあとの回転で粗い絵に戻らない |
| すぐ出る (依頼にはないが Range で読む以上は効く) | fast (20 ms、50 Mbps) で、ページの遷移から完全な絵まで p50 600 ms、粗い絵まで 250 ms |
| 見ている範囲の分だけ読む | 原本の WebP タイルで同じ視点を読むときの 0.35 倍以下のバイト、データ経路の時間 0.5 倍以下。最初の視点 1.1 MB、20 リクエスト以内 |
| GitHub Pages に置ける | データ 9 MB 以内 (1 ファイル) |
| 配るコードは小さく | gzip 12 KB 以内 |
| GPU メモリを控えめに | ページ自身の見積もり 64 MB 以内、JS ヒープ 40 MB 以内 |
| PC のブラウザ | 1280×800、DPR 1、CPU スロットルなし |
| 正しく出ている | 13 の機能確認 (下の「確かめたこと」) |

## やらないこと

画像の貼り付け、文字、水面、建物、地球儀、影を落とすこと、等高線、高さの読み出し UI、タッチ、geomorph、区画の外への移動、実行時の WebP の復号。

## データ

Mapterhorn の全球標高 PMTiles (664 GB、z0-12、512 px の WebP lossless) を、手元の実ファイルから `tools/pmtiles.ts` で Range 読みした。メタデータにはエンコードの記述がなく、山頂の画素 RGB(142,186,208) を Terrarium の式で読むと 3770.8 m、Mapbox の式では 92 万 m になるので Terrarium と決めた。z11 は z12 の 2x2 平均 (差の p99 0.002 m) なので、z12 から平均で作った段 k は原本の z(12-k) と同じ標本になる。

区画は z12 のタイル 6x6、47.86 km 四方 (3072x3072 標本、セル 15.58 m)。タイル境界に揃えたので、各段のチャンクは原本の 1 タイルにちょうど 4x4 で収まり、原本と同じ標本で比べられる。代わりに山頂は中心から西へ 4.7 km、南へ 3.2 km ずれる。

## 設計

- ファイルは `fuji.terr` 1 本 (7.83 MB)。64 B のヘッダー、1 チャンク 8 B の索引 (長さ、高さの最小と最大、スカートの深さ)、チャンク本体を粗い段から (L3 9、L2 36、L1 144、L0 576)、段の中は Morton 順に並べる。オフセットは長さの累積なので持たない。
- チャンクは 128 セル。131x131 標本 (頂点 129x129 と、法線のための縁 1 標本) を、0.25 x 2^k m に量子化して平面予測 a+b-c の残差を Rice 符号にする (約 4.7 bit/標本)。縁も実データで、区画の外周の分は外側 1 周の z12 タイルから取った。
- 最初のリクエストは先頭 96 KiB に固定した。ヘッダー、索引、L3 全部 (97,999 B まで) と L2 の頭が入る。このリクエストは `index.html` のインラインスクリプトが、モジュールを読む前に始める。
- 視点が変わったら、L3 の 9 個の根から四分木をたどって選ぶ。視錐台の判定には索引の min/max を使い、セルの投影幅が 1.5 px を超える間は細かくする。足りないチャンクはオフセット順に並べ、8 KiB 以内の隙間を結合して Range で読む。届いたら 4 ms ずつに切って復号し、テクスチャに入れる。揃うまでは、その親を代わりに描く (置き換え式。重なりも穴もない)。
- GPU には R16UI のテクスチャ配列 (131x131x765、26.3 MB) を最初に確保し、1 チャンク 1 レイヤーにする。頂点バッファーは持たない。gl_VertexID から格子の位置とスカートかどうかを決め、高さはテクスチャから引く。インデックス (u16、0.2 MB) は全チャンクで共有し、1 フレームの描画は drawElementsInstanced の 1 回。
- 法線は隣の 4 標本の中心差分。陰影は北西、高度 40° の太陽の Lambert で、高さで色を変え (緑、オリーブ、茶、スコリアの灰、3400 m から白)、空気の密度で重みを付けた霧を掛ける。地球の丸み (屈折込み) は目の真下からの距離で下げる。
- 段の境目: 内側の頂点は標本の中心に置き、辺の頂点だけをチャンクの枠の上に置いて、枠をまたぐ 2 標本の平均の高さにした。段の違う隣とも同じ線で接するので、縦のスカート (深さはベイクで測る) で隙間が塞がる。
- カメラは軌道カメラ。左ドラッグで回転と pitch (8〜89°)、右ドラッグか Shift+ドラッグで注視点の移動、ホイールで距離 6〜100 km。指を離すと 300 ms の慣性。目はその下の L0 チャンクの最大標高より 150 m 上に保つ。描くのは変化があったときだけ。
- 静止して 300 ms たつと、今の注視点、pitch、距離で一周したときに要るチャンクの和集合 (2° ごとに 180 回選ぶ) を低い優先度で先読みする。依頼が「回したい」なので、回し始めたときに待たせない。

## 確かめたこと

真値は DuckDB で別に作った。GDAL の XYZ 出力を `floor(x)`、`floor(y)` で結合し (整数への cast は偶数丸めで隣の画素が混ざる)、avg で段を作り、全チャンクの min、max、sum と 124 地点の近傍を出す。ベイクは Node の結果と 1 つでも違えば失敗する。ベンチでは画面と位置ターゲット (画素ごとの xyz と段) を読み戻して、次を確かめる。

- 画面に出た地表の高さが真値と一致する (5 視点で 27〜124 地点、最大の差 3.2 mm)。全 765 チャンクの復号値が真値と一致する。
- 穴がない (5 視点と回転中 12 地点)。L0 の継ぎ目で陰影に段差がない (対照との比 1.056)。北西向きの斜面が南東向きより明るい (130 と 83)。close 視点の山頂が L0 で白く描かれる。
- 原本をブラウザで読んで描いた絵との高さの差が p99 0.41 m。ブラウザの WebP 復号の値が GDAL と 1 ビットも違わない (81 地点)。
- 慣性が止まったら描かない。最小距離まで寄っても目が地面に潜らない。先読みのあとは回しても粗い絵に戻らない。

## 計測で分かったこと

最終計測は 3 回 (load average 2〜3)。

- 原本との比較 (同じ視点、同じ選択、ローカルの実ファイルを同じサーバーとネットワーク条件で): default で自前 971 KB、18 リクエスト、225 ms に対し、原本 4,963 KB、17 リクエスト、891 ms (うち WebP の復号 105 ms)。バイト 0.20 倍、時間 0.25 倍。ほかの視点もバイトは 0.23〜0.28 倍。原本のバイト数は、ベイク時に実ファイルから数えた値とバイト単位で一致した。
- 最初の絵: 完全な絵 p50 301 ms、粗い絵 144 ms。最初のリクエストをインラインスクリプトで始めると、main.ts で始めるより 20 ms ほど早い (p50 320 ms と 342 ms)。
- 範囲を結合する隙間は、設計時の 32 KiB より 8 KiB のほうが速かった (224 ms と 241 ms)。0 なら 229 ms、128 KiB なら 363 ms。20 ms、50 Mbps では、リクエストを減らすより余計なバイトを減らすほうが効く。
- フレーム: 回転 frame_ms p95 2.9 ms、gpu_ms p95 2.0 ms、cpu_ms p95 0.11 ms、選択 p50 0.05 ms。close 視点 3.5 ms、low 視点 2.4 ms (p95)。全部を L0 で描いても (1,950 万三角形) GPU は 4.5 ms で、LOD の得は GPU より読むバイト数 (全部なら 7.8 MB) のほうにある。
- 先読みのない回転では 1 フレームの全費用が p50 1.5 ms、最大 9.0 ms、ズームでは p95 3.7 ms、最大 5.5 ms。
- 最初の版は、どの段でも頂点を標本の中心に置いていたので、段の違う隣との間に半標本ぶんの溝ができ (L0 と L1 で 7.8 m)、縦のスカートでは上から見て塞げなかった。辺の頂点を枠の上に移して直した。
- 先読みを設計どおり「L1 と L2 の残り全部」にした版は、回転の 120 フレームのうち 3 フレームで L0 が足りず粗い絵に戻った。一周の和集合 (162 チャンク、1.69 MB) にして 0 になった。
- 霧を距離だけで決めると (設計時の exp(-d/45 km) では 40 km 先が白くなり、exp(-d/120 km) でも)、真上 70 km からの視点で斜面の明暗の差が 29 に縮み、検査に落ちた。空気の密度を視線に沿って平均すると 47 になった。
- ハーネスの Chromium は vsync がないので、rAF の間隔をそのまま測ると GPU の待ち行列があふれて 743 ms の停止が出た。60 Hz を真似て rAF を読み飛ばすと、描かない rAF が約 18 ms 間隔になり、それを測ってしまった。毎 rAF で描いて 1 画素の読み戻しで待つ形にした。アイドルのあとの最初の rAF は約 17 ms 後に来るので、先に 1 フレーム描いてから測る。
- GPU メモリはページの見積もりで 60.4 MB (テクスチャ 26.3 MB、4x MSAA の既定フレームバッファー 33.9 MB)。nvidia-smi で見た Chromium の GPU プロセス全体は、読み戻し用のターゲットと原本のタイルを使うベンチ中に 158〜206 MiB だった。
- 山頂の標本は 3770.81 m で、実際の 3776 m より 5 m 低い。15.6 m 四方の平均だから。Mercator の格子を中心の縮尺で使っているので、四隅では最大 65 m ずれる。

## 残っていること

- 配布時の出典: `fuji.terr` は Mapterhorn の標高データを富士山周辺で再標本化・再符号化したもの。Mapterhorn の [帰属情報](https://download.mapterhorn.com/attribution.json) は、日本の元データに国土地理院の基盤地図情報（数値標高モデル）が含まれることを示す。Mapterhorn の[承認書](https://github.com/mapterhorn/mapterhorn/blob/main/source-catalog/jpdem10a/LICENSE.pdf)には「測量法に基づく国土地理院長承認（使用）R 8JHs 131」とある。国土地理院の[承認申請 Q&A（Q1-24）](https://www.gsi.go.jp/LAW/2930-qa.html)では、使用承認を得て作成した成果の二次利用に追加申請は不要とされる。Mapterhorn は[配布案内](https://github.com/mapterhorn/mapterhorn/blob/main/distribution/README.md)で地域別ミラーを案内している。ページ上では Mapterhorn と国土地理院の出典、加工の事実、承認番号を明示する。
- LOD の切り替えのポップ (geomorph なし) は目視で確かめていない。
