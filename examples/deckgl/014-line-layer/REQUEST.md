# deckgl-014-line-layer: 郡間のネット人口移動を直線で

## 依頼内容

> 米国の郡（county）間の人口移動上位1,500組を直線の LineLayer として描き、東向き・西向きで色を分けたい。ドラッグでパン、ホイールで拡大縮小でき、外部ライブラリなし・Canvas 2D で最速・最小に実装する。

元例: [deck.gl - LineLayer](https://deck.gl/examples/line-layer/)（データは deck.gl ArcLayer 用の counties.json）

## 設計の意図と判断

1. **原データの二重格納をベイクで畳む**
   - counties.json の `flows` は郡ペアの両方向を `flows[t][s] === -flows[s][t]` で持つ完全な反対称データ。全レコードを描くと各線分が2回、逆色で描かれ、後から描いた橙色が上に残って水色が見えなくなる（最初の計測で実際にそうなった）。s < t の1件に畳み、西→東に固定して符号を「ネットの東西移動」の向きに揃える。
2. **ワールド座標の Path2D を2本だけ stroke**
   - 読み込み時に東向き・西向きの Path2D を1回だけ作り、毎フレームは CTM にスケールと平行移動を掛けて stroke を2回呼ぶ。線幅は `1.5/scale` で一定の CSS px。
3. **線分数はラスタライズ予算で決める**
   - `redraw_ms` は Canvas コマンド発行しか測らないため 1 ms 未満でも、実際のラスタライズはフレーム後半に効く。CPU バックの canvas では 3,000 本で frame_interval p95 35.6 ms、2,000 本でも 18.8 ms と余裕がなく、1,500 本で 15.5 ms（p50 11.6 ms）だったので 1,500 本を採用。
4. **画面外の世界コピーは描かない**
   - ズーム 3.4 では世界のコピー1枚しか画面に掛からない。2枚目を丸ごと描くのは無駄なので、画面と交差しないコピーはスキップする。

## 計測結果

| 再描画 redraw_ms p95 | 1.05 ms |

| コード gzip | 2,893 B |

| 検証チェック | 4 / 4 PASS |

## 検証チェック

- `flow-directions-visible`: 画面全体を読み戻し、水色（r<110, g>110, b>150）と橙色（r>150, 80<g<200, b<90）がそれぞれサンプルの1%超を占める。
- `line-layer-visible`: 長い順に最大25本を走査し、東西それぞれ最長の線の中点 9×9 px に自色のピクセルがあることを確認。
- `lines-move-with-pan`: panBy(50, 30) で中点の画面座標がちょうど (50, 30) 動き、移動先にも同じ色がある。
- `wheel-zoom-keeps-point`: zoom 3.4→4.2 でカーソル下の中点のずれ < 1.5 px。

## 補足

- 最初の実装は 5,000 レコード（＝2,500 ペアの重複）を描き、画面がほぼ橙一色になった。正方向の色チェックが FAIL したことで気づき、bake でペアを畳んで解決した。
- その状態でも frame_interval_ms p95 は 31.6 ms で予算超過。線分数を 1,000 / 1,500 / 2,000 / 3,000 と振って測り（p95 11.5 / 15.5 / 18.8 / 35.6 ms）、1,500 を採用した。
- 画面外コピーのスキップは正しさのための最適化で、フレーム間隔への寄与は測定誤差の範囲だった（3,000本時 35.84 → 35.56 ms）。
