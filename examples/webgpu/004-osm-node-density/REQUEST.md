# webgpu-004 東京23区の OSM ノード密度 (WebGPU)

## 依頼

> 東京23区の OSM の全ノード（約 966 万点）の密度をヒートマップで見たい。拡大・移動したら、タイルの粗い集計ではなく、その画面の解像度で数え直してほしい。PC のブラウザで。

[04-osm-node-density](../../04-osm-node-density/REQUEST.md) と同じ依頼です。04 は WebGL2 の加算ブレンドで数えます。この例は同じものを WebGPU の compute で数え、同じ条件で比べるために作りました。

## そろえたもの

- データ: 04 の `nodes.bin` をそのまま読む (9,658,062 点、gzip 後 17.5 MB)
- 点の並び: Morton 順を 128 本のストライドに分けて並べ直す (04 と同じ)
- カメラの式、画面 (1280×800、DPR 1)、色の段階、計測の経路 (23 区全体から渋谷駅へ 256 倍までズームして戻る 300 フレーム、全体表示と 256 倍表示で止めた各 60 フレーム)
- ブラウザ: 同じ Chromium を Xvfb 上で画面ありで起動する (`display: xvfb`)。04 は `MFS_DISPLAY=xvfb bin/mfs bench 04-osm-node-density` で同じ設定で測る。WebGL2 の数字は headless と変わらない

違うのは数え方だけです。

| | 04 (WebGL2) | webgpu-004 (WebGPU) |
| --- | --- | --- |
| 数える | 1 px の点を R32F に加算ブレンド | compute で画素ごとの u32 に atomicAdd |
| 最大値 | 4×4 ごとの max を 1×1 まで縮約 | ワークグループ内で atomicMax し、1 ワークグループ 1 回だけ全体へ atomicMax |
| 色付け | 全画面の三角形 | 同じ |

1 フレームは、3 回の dispatch (数をゼロにする、数える、最大値) を持つ compute パス 1 つと、色付けの描画パス 1 つです。

## 計測結果

RTX 3060、Chromium 156 (Xvfb 上で画面あり)、2026-10-30。04 と交互に 2 回ずつ測り、2 回とも同じ値になった (load average 6〜8、GPU は空き)。値は 2 回目。

| | 04 WebGL2 | webgpu-004 | |
| --- | --- | --- | --- |
| ズーム経路の GPU 時間 (`gpu_ms`) p50 / p95 | 0.82 / 2.65 ms | 0.19 / 0.67 ms | 約 4 倍 |
| 全体表示の GPU 時間 (`whole_gpu_ms`) p50 | 2.64 ms | 0.51 ms | 5.2 倍 |
| 256 倍表示の GPU 時間 (`street_gpu_ms`) p50 | 0.77 ms | 0.19 ms | 4.0 倍 |
| ズーム経路のフレーム時間 (`frame_ms`) p50 / p95 | 1.06 / 2.95 ms | 2.30 / 2.37 ms | |
| 全体表示のフレーム時間 (`whole_frame_ms`) p50 | 2.92 ms | 2.30 ms | |
| 初回描画 (`first_frame_ms`) p50 | 658 ms | 965 ms | |
| 配るコード (gzip) | 2,762 B | 3,967 B | |
| ブラウザ全体の RSS | 1,383 MB | 1,504 MB | |

予算 (04 と同じ) と検証の項目はすべての反復で通った。

- GPU 時間はどの表示でも 4〜5 倍速い。どちらも timestamp で、04 は `EXT_disjoint_timer_query_webgl2`、この例はパスの timestampWrites で測る。
- フレーム時間は、ズーム経路の p50 で WebGL2 のほうが短い。WebGPU は描いてから `onSubmittedWorkDone` が解決するまで約 2.3 ms かかり、GPU の仕事が 0.19 ms でもこれより短くならない。WebGL2 は `readPixels` で同期的に待つので、この床がない。表示のたびに完了を待つ使い方をしない限り、利用者に効くのは GPU 時間のほう。
- 初回描画は WebGPU のほうが約 0.3 秒遅い。内訳 (アダプタとデバイスの取得、パイプラインの作成、38 MB のバッファの転送) はまだ測っていない。
- JS ヒープは、検証のために計測ページが読み直す 38 MB の影響を受けるので、比べていない。転送量も同じ理由で両方とも 2 倍 (75 MB) になっている。

## 計測で分かったこと

- 全点が範囲外の 256 倍表示でも 0.19 ms かかり、どの点の並びでも変わらない。全点 (38.6 MB) を読むだけで約 200 GB/s で、RTX 3060 のメモリ帯域 (360 GB/s) の半分を超える。これより速くするには、読む量を減らす (点を小さく詰める、画面外のブロックを飛ばす) しかない。
- 点の並びの影響は、加算ブレンドより atomicAdd のほうがずっと小さい。全体表示の GPU 時間は、ストライド 1 (Morton 順のまま) で 0.96 ms、16 と 128 で 0.51 ms、1024 で 0.63 ms。04 のブレンドは 1 で 11.7 ms、128 で 2.6 ms だった。
- 画素ごとの数を CPU の数え直しと比べると、ピクセルの境目ぎりぎりの点だけが違うピクセルに入る。WGSL は割り算の誤差 (2.5 ULP) と、掛け算と足し算をまとめて丸めること (FMA) を許すため。境目から 1e-3 px 以内の点はどちらに入ってもよいとすると、全ピクセルが一致する。
- この比較の途中で、04 から引き継いだ並べ替えの式の不具合が見つかった。ストライドの間隔を一律に ceil(n / S) にしていたので、128 本の最後のストライドが配列の外に 49 点はみ出していた。型付き配列は範囲外への書き込みを黙って捨てるので、南東の 49 点が消え、北西の角 (0, 0) に存在しない点が 49 個できていた。合計は変わらないので count-conservation は通っていた。04 とこの例の両方で直し、全体表示の画素ごとの数を CPU と比べる検査を足した。古い式ではこの検査が落ちる (04 で 41 ピクセル、この例で 48 ピクセル)。
